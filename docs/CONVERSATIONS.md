# Conversation editing and quoting

Both user messages and assistant replies support a plain save that preserves the complete original conversation as an archive, keeps following messages and composer input, and makes no provider request. Manually edited replies retain actual generating evidence and join reply versions with an explicit manual marker. Per-message editing drafts survive cancellation, normal close/restart and complete backups; conflicts retain the old draft until an explicit discard reloads current text. See [MESSAGE-EDITS.md](MESSAGE-EDITS.md).

User-message editing opens a native themed dialog with the existing text and retained attachment names. Sending an edit creates a linked conversation branch containing the preceding context, edited user text and original attachments. The complete original conversation and its later replies remain available. The branch header can reopen its original conversation; a missing original simply removes that action. Ordinary forks now retain the same ancestry metadata.

The editor captures the selected provider, model, assistant, project and extension selection when opened. The main process validates those choices before saving the new branch. Invalid configuration, concurrent history changes and an initial persistence failure leave the original conversation intact. The editor keeps the entered text after rejection, and cancel/Escape makes no model request. Sending an edit does not consume the separate composer draft. Global conversation-navigation shortcuts are suspended while the editor is open; Ctrl/Command Enter resends a user edit in a new branch or plain-saves an assistant edit, and Ctrl/Command S plain-saves either role.

Replay requests include the chosen user-message ID, action and SHA-256 history revision. Message data is normalized through the same schema in the renderer and main process so key ordering from streaming cannot create false conflicts. Revisions include message content/status, attachments and tool evidence; changing unrelated thread metadata does not change the history revision. The main process checks again inside the serialized vault update, after any queued changes. A reserved or active source response prevents editing it.

Regeneration validates configuration and history before replacing the most recent user turn in one vault update. That same transaction preserves the complete preceding conversation as an archived reply version, including model/usage/tool/source evidence and its saved composer draft. It uses the saved user text and attachments and preserves preceding context, without adding a duplicate user message. Only the latest user message may be retried. Validation and an initial write failure retain the preceding reply. A provider failure or stop after a successful retry start creates a visible failed/stopped version; the earlier replies remain available. Exact preview and selected-version continuation, independent drafts, limits and complete backup behavior are documented in [REPLY-VERSIONS.md](REPLY-VERSIONS.md).

Quoting appends Markdown blockquote text to the existing composer draft and focuses the caret at its end. A selection wholly inside the chosen message quotes that passage; otherwise the complete message text is used. Quoting makes no provider request and does not send automatically. Empty text and a combined draft exceeding the 256 KB submission limit are rejected rather than silently truncating user text. A shorter passage can be selected for an oversized reply.

Unit tests cover canonical revisions, attachment/tool changes, quote limits, target validation, saved attachments, failed writes, active sources, changes/deletion during queued persistence and restored ancestry. Desktop verification uses the real renderer/preload/main/provider path for selected-text quoting, cancel/whitespace/shortcut behavior, attachment-preserving editing, retry, concurrent-history rejection, light/dark minimum-window controls and branch restoration. The text-file picker uses a dialog fixture only in the test process.

Composer drafts now retain exact text, complete text attachments and provider/model/assistant/project/mode/extension choices separately for each conversation and for new chat. Switching restores that owner's draft. Editing into a branch copies the current composer draft to the new branch while keeping the source draft. Reopening the original restores its own draft. Startup restores the last active conversation, falling back to new chat if its owner is absent. Removed or disabled selections are filtered on restoration; project modes are reset to chat when their project is absent.

The renderer stages changes immediately in memory and saves after a 250 ms debounce. Overlapping writes are serialized, input received during persistence is saved next, and failed writes retain the latest draft for retry. Normal window closing flushes pending drafts, including attachments, before exit. A failed flush keeps the window; a timeout offers cancellation or explicit closing. A cancelled timeout safely ignores its late save receipt. Forced termination can lose changes that have not reached persistence.

Sending snapshots the draft and saves it before submission. Its canonical SHA-256 revision excludes the save timestamp and includes text, attachments and selections. The first conversation write consumes only a matching stored draft in the same transaction. Validation or initial persistence failure leaves it intact. Newer input and other owners remain intact, and navigating away during submission does not restore the sent draft or replace the newly opened composer. A provider failure after the turn has been saved leaves a visible failed reply in history. Deleting a conversation removes its draft as part of the same workspace update.

Workspace backup and restore request a renderer flush through the checked main-window IPC boundary before opening their dialogs. This applies to the settings controls, native menu and bridge calls, and includes code-editor drafts as well as composer drafts. A failed or timed-out flush aborts backup/restore. Complete backups retain draft attachments, active ownership and selections; restored skills and plugins receive new IDs in both conversation history and drafts. Restored plugins still require fresh grants. The settings restore also replaces the live renderer's draft store so an old local draft cannot overwrite the restored one.

Draft storage accepts at most 100 owners and 32 MB of encoded draft data; it reports limits without evicting existing drafts. Empty text with no attachments clears its owner. Whitespace and attachment-only drafts remain recoverable. Older schema-version-one backups default to no composer drafts.

Additional unit tests cover ownership, schema migration, quotas, restart/backup, current grants/scopes, remapping, matching consumption, concurrent input and failed persistence. Native tests exercise switching, backup/restoration, actual filesystem write rejection, normal close/restart, a deliberately delayed close callback, missing-key rejection, sending while navigating, attachment delivery and owner-specific deletion. Native file/confirmation dialogs use fixtures in the test process; the close delay and one filesystem replacement delay are deliberate test injections.

Richer graphical branch navigation, temporary conversations and parallel multi-model comparisons remain pending. Sequential regeneration can compare different selected models through preserved reply versions. Ctrl/Command Enter sends an edited user message in a new branch or saves an edited assistant reply; Ctrl/Command S performs a plain save for either role.
