# 项目读取与完整工作台隔离

`workspaceProject()` 先按原有 IPC 标识规则验证项目 ID，再通过 `WorkspaceVault.project()` 读取当前已提交项目的独立副本。文件、Git 和终端接口继续使用同一项目范围检查；不存在或已删除的项目仍返回原有明确错误。

旧实现通过 `vault.snapshot().projects.find(...)` 读取项目。虽然请求只需要项目标识与路径，`snapshot()` 会复制所有聊天、附件、资料和草稿。完整套件恢复大型工作台后，终端提示符检查每 100 ms 调用一次 `terminalList()`，每次都会额外复制整份数据。这里修复这一确定的读取成本，不把它直接认定为远端 Shell 启动失败的唯一原因。

验证边界如下：

- 旧实际安装包在新增原生回归中产生 9 次整工作台复制：8 次终端列表读取和 1 次文档读取。修复后的真实开发应用为 0 次，两种情况均使用实际 IPC。
- 新 accessor 的单元测试验证返回值隔离、原型式标识、未知项目、排队更新、非法更新失败和删除。只返回已提交的项目，不缓存旧项目，也不向调用方暴露内部对象。
- 串行基准使用同一确定性生成器创建 297 个对话、20 份大型 Unicode 消息及独立临时项目目录。两份工作台均为 84,064,376 字节；临时项目路径不同，所以完整文件哈希不同。40 次读取的整工作台复制从 40 次降为 0 次，各份主文件和备份保持字节不变。该基准衡量读取成本，不代表 Shell 初始化耗时、IPC 延迟或峰值内存。
- 原有终端提示符期限仍为 10 秒，轮询仍为 100 ms；模型首次显示和完成期限也保持原值。完整套件需再次验证大型备份恢复后的实际终端、文件读取、对话分支及模型比较。
- `verification/hosted-comparison-starts-terminal-failure-result.json` 保留此前 `a124a86` 在远端通过 681 项单元测试、打包审计和 164 项桌面检查后失败的现场。实际 PowerShell 7 仍在运行，但没有提示符；其后资源采样不构成 Shell CPU、调用栈或准确原因证据，9 份必需运行记录缺失。

当前组件证据为 `verification/project-access-component-result.json`。完整源码、同一应用体的安装与便携分发、远端完整流水线和剩余能力／UI 范围须分别完成，不能用旧应用体的通过记录替代。
